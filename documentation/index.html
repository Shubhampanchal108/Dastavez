Law Enforcement Focus

Why DMS Was Built for Police Stations

Police Stations (Thana), Case Diaries (CD), Seized Evidence Malkhanas, and Court Evidence Chambers are the bedrock of criminal justice. Yet, the traditional infrastructure relies on vulnerable physical papers that compromise trials. DMS was built to modernize this entire pipeline.

Mission: Flawless Legal Admissibility

DMS bridges the critical evidentiary gap between the Police Station (Thana), Forensic Science Laboratory (FSL), Public Prosecutor (PP), and the Judicial Magistrate Court. By computing immediate SHA-256 cryptographic hashes and anchoring them to a decentralized Solidity smart contract registry, evidence cannot be backdated, modified, or swapped.

Security & Compliance

Security-First Philosophy

DMS is designed from the ground up for zero-trust environments where forensic proof, regulatory chain of custody, and cryptographic truth are non-negotiable.

Cryptographic Secret Isolation

Never commit backend/.env, database credentials, Cloudinary API secrets, JWT signature keys, EVM wallet private keys, or RPC credentials to Git. Use .env.example exclusively as a sanitized configuration scaffold.

Authoritative Backend RBAC

All document access, mutation, classification, custody transfer, and proof creation are governed by server-enforced Role-Based Access Control (ADMIN, INVESTIGATOR, FORENSIC_OFFICER, VIEWER). Client credentials are authenticated before every data read.

Device-Bound Biometrics

Web login requests trigger out-of-band mobile verification challenges. The user approves authentication using device biometric sensors (TouchID/FaceID/Fingerprint). The website JWT is never transmitted over the challenge approval channel.

Tamper-Proof Audit Logging

Every operation across authentication, upload, AI validation, version creation, custody transfer, share access, and backup verification is recorded with actor IDs, IP timestamps, and payload hashes into an append-only audit ledger.

Interactive Diagrams

System Workflows & Lifecycles

Inspect end-to-end execution flows step-by-step. Select any workflow tab below to see the interactive protocol sequence.

1
Primary Password Validation
Web Portal → POST /api/auth/login
The user submits email and password. The backend checks PBKDF2/Argon2 password hash. If valid, rather than issuing an access token immediately, it checks if user has registered an authenticator device or requires OTP challenge.
2
Challenge Generation & Mobile Polling
Backend Engine → UUID Nonce Challenge
A cryptographic challenge UUID is generated with a strict 2-minute expiration. The mobile Flutter authenticator receives or queries pending challenges bound to the user's public key.
3
Biometric Sensor Authorization
Flutter Mobile App → Local Biometrics
The Flutter app displays the login attempt context (Client IP, Timestamp, Browser Agent). The user confirms with FaceID / TouchID / Fingerprint. The device signs the challenge payload with its secure enclave private key.
4
Challenge Approval & JWT Issuance
Backend → POST /api/auth/authenticator/complete
The backend verifies the cryptographic signature against the registered device public key. Upon confirmation, the web portal completes the exchange and receives a scoped JWT token with authoritative RBAC claims.
1
Stream Upload & SHA-256 Hashing
POST /api/documents/upload
File stream is ingested while computing the SHA-256 cryptographic digest in 64KB chunks. Duplicate detection query runs simultaneously to reject identical binary copies if configured.
2
Cloud Storage Persistence
Cloudinary Upload Service
The binary asset is stored in encrypted cloud blob storage with an immutable public identifier and delivery URL. Document version #1 is recorded with file size, MIME type, and creator metadata.
3
Text Extraction & OCR
Extraction Service (pypdf / OCR)
The text layer is extracted from PDF pages. If scanned or raster image pages are detected, optical character recognition produces normalized UTF-8 text tokens.
4
Groq LLM Semantic Classification & Metadata Check
AI Service → Groq Llama 3
Extracted text is sent to Groq with strict JSON output schemas. The AI determines document classification (FIR, Affidavit, Invoice, Contract, ID), confidence scores, and verifies consistency with user-supplied metadata.
1
Compute Document Proof Hash
POST /api/documents/{id}/blockchain-proof
Generates a Keccak-256 proof hash incorporating Document ID, Version Number, File SHA-256, and Creation Timestamp: keccak256(doc_id + version + sha256 + timestamp).
2
Smart Contract Transaction Dispatch
Solidity: registerProof(bytes32, bytes32)
The backend signs an EVM transaction dispatching registerProof(proofKey, proofHash) to the DocumentIntegrityRegistry smart contract on Ganache, Ethereum, or Polygon.
3
Decentralized Notarization Confirmation
EVM Block Receipt & Record
Transaction receipt is mined. The transaction hash, block number, and contract address are linked to the Document record in the PostgreSQL database.
4
Independent Verification Audit
GET /api/documents/{id}/blockchain-verify
Any auditor can request real-time on-chain verification. The system queries the smart contract via RPC and compares the on-chain stored proof with the active document hash, proving zero tampering.
1
Custody Transfer Initiation
POST /api/documents/{id}/custody/transfer
The current custodian creates a transfer request specifying the target recipient (e.g., Forensic Lab, Prosecutor, External Auditor), purpose of transfer, and secure transfer protocol.
2
Pending State & Integrity Locking
Status: TRANSFER_PENDING
The document custody state transitions to pending. Audit event is recorded, and the target recipient receives an in-app custody transfer notification.
3
Custody Acceptance & Physical/Digital Receipt
POST /api/custody/{transfer_id}/receive
The recipient accepts custody, inputting physical verification condition notes or digital acknowledgment. The system re-hashes the active file to certify integrity at the moment of handover.
1
Automated Backup Snapshot
POST /api/backups/create
The backup engine serializes database tables into JSON/SQL dumps and bundles asset manifests into a compressed, timestamped archive, uploaded to private Supabase Storage buckets or local backup storage.
2
Non-Destructive Isolated Restore Test
POST /api/backups/restore-test
A temporary isolated sandbox database is provisioned. The backup archive is unpacked, tables are hydrated, all document versions and hashes are checked for 100% integrity, and the sandbox is cleanly unmounted.

SHA-256 Deduplication Engine

Every ingested document is hashed using streaming SHA-256 cryptographic digests. Duplicate checks operate in real-time, preventing identical binary storage, conserving storage costs, and cross-linking redundant uploads.

hashlib Streaming IO Zero Collisions

Groq AI Semantic Classification

Harnesses high-speed Groq LPU inference to classify legal documents (FIRs, Court Orders, Affidavits, Invoices) and detect discrepancies between declared metadata and extracted document content.

Groq Llama 3 JSON Mode <350ms Latency

Solidity Blockchain Notary

Anchors document integrity directly onto an EVM-compatible blockchain. Produces immutable cryptographic proof receipts that allow independent verification even if the primary database is compromised.

Public Endpoint ▾
Validates primary credentials. Initiates either an OTP challenge or a mobile authenticator challenge based on user configuration.

Documents & Upload Engine

POST /api/documents/upload
Bearer Token (Admin/Investigator) ▾
Streams multipart document upload, calculates SHA-256 hash digest, checks exact duplicates, uploads to Cloudinary, and triggers text extraction.
curl -X POST http://127.0.0.1:8000/api/documents/upload \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -F "file=@case_evidence_402.pdf" \
  -F "case_id=c148f936-3a6a-4d43-85f0-571217e99742" \
  -F "document_type=Evidence_Record" \
  -F "department=Forensics" \
  -F "sensitivity=Confidential"
import requests

headers = {"Authorization": f"Bearer {access_token}"}
files = {"file": open("case_evidence_402.pdf", "rb")}
data = {
    "case_id": "c148f936-3a6a-4d43-85f0-571217e99742",
    "document_type": "Evidence_Record",
    "department": "Forensics"
}
res = requests.post("http://127.0.0.1:8000/api/documents/upload", headers=headers, files=files, data=data)
print(res.json())
GET /api/documents/{document_id}/duplicates
Bearer Token ▾
Queries all documents in the repository matching the identical SHA-256 hash of the specified document.

Blockchain & Integrity Proofs

Bearer Token ▾
Interrogates the smart contract registry on the configured EVM network, compares on-chain proof hash with local file hash, and returns cryptographic integrity status (VERIFIED, MISMATCH, or NOT_ANCHORED).

Local Setup & Quickstart Guide

Step-by-step instructions to initialize the backend FastAPI service, database migrations, Next.js frontend, and Flutter mobile authenticator.

1. Backend Setup (FastAPI + PostgreSQL)

Ensure Python 3.11+ and PostgreSQL 14+ are installed on your host system.

PowerShell (Windows) 
# Navigate to backend directory and create virtual environment
Set-Location backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1

# Install dependencies and setup environment template
pip install -r requirements.txt
Copy-Item .env.example .env

# Run database migrations with Alembic and launch dev server
alembic upgrade head

PowerShell / Bash

# Start Next.js development server
npm run dev

Flutter CLI
